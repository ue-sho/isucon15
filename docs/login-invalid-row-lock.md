# 不正ログインのユーザー行ロック削減

2026-10-31。作業ブランチ `perf/login-auth-filter`、起点はmain `7e57093`。別の作業ツリー `/tmp/isu15-login-auth-filter` へログイン改善だけを切り出した。

PR #48は画像署名のHMAC計算、PR #49は画像GETの探索ヒントとファイルキャッシュ同期処理。この変更は`user_api.ts`、`auth-permission-db.test.ts`、本記録の3ファイルで、両PRとの変更ファイル重複はない。画像・JPEG・署名計算には変更を加えない。

## 入力と仮説

ユーザー提示のasia1集計では、ログイン990件のうち820件が4xx、170件が2xx。全status合計626.567秒、平均0.633秒。4xxの内訳・CPU使用率・DB待機状況はこの集計からは不明。

コードでは秘密鍵とstatusの検証より先にusernameだけで`FOR NO KEY UPDATE`していた。誤った秘密鍵でもユーザー行ロックを待ち、取得後はrollbackまで他の行更新を待たせる。認証条件をSELECTのWHEREへ移し、誤った秘密鍵・非activeユーザーを行ロック対象から除く。

これはロック競合を減らす仮説であり、asia1のCPU負荷の主因を特定したものではない。4xxすべてがこのSQLへ到達するわけでもない。通知はSSEの接続待機時間を含むため、提示された合計972.031秒をCPU時間と解釈しない。プロフィール画像は同期JPEGデコードを行っているが、提示集計だけでは失敗原因やCPU寄与を特定できないため今回は変更しない。

## 維持する動作

正常ログインのユーザー行ロック、トランザクション、旧セッション失効・新セッション作成を維持する。追加のDB往復はない。存在しないユーザー、誤った秘密鍵、退会済みユーザーはいずれも401 `invalid_credentials`。正常ログインのロック待機中に退会がcommitした場合も、PostgreSQLが条件を再評価して401を返す。

DBスキーマ・キャッシュ・初期化・永続化・リージョン経路の変更はない。戻す場合は`user_api.ts`のログインSELECTと秘密鍵/status検証を元に戻す。

## ローカル検証

本番とは独立した一時PostgreSQL 16を使用。Node.jsは手元の24.12.0に`--harmony-temporal`を付けた。本番想定のNode.js 26での確認は未実施。

- 別トランザクションが対象ユーザー行を保持している状態で、旧SELECTは設定した100msのlock_timeoutに達し、101msで55P03。変更後の誤った秘密鍵のHTTPログインは2msで401。この比較は人工的なロック競合試験であり、競技ベンチの改善率ではない。
- 同じ状態で正しい秘密鍵はロック待機することを`pg_blocking_pids`で確認。保持側で退会をcommit後、401になることを確認。
- 既存の同時ログイン・セッション失効、同名登録、投稿・権限・公開範囲変更を含むDB統合テスト6件成功（権限432条件を含む）。
- `npm run check`成功。
- Nodeテスト全体は82件成功・DB等の明示指定が必要な12件skip。認証DB統合テストは別実行で上記6件を確認。

再現は新規の一時PostgreSQLを用意し、`webapp/nodejs`で`AUTH_PERMISSION_TEST_PG_PORT=<port> node --harmony-temporal --test test/auth-permission-db.test.ts`。指定したローカルDBサーバー内に新しいテストDBを作成する。
