# プロフィール画像のJPEG検証を専用workerへ分離

ベンチ23332（ユーザー報告5379点、main `174cc851`）ではasia1のCPU平均84.9%、プロフィール画像の400応答115件・平均3.118秒を観測した。通常APIも遅く、同期JPEG検証によるイベントループ停止が改善候補になった。HTTP時間は受信・待機等も含み、すべてがJPEGのCPU時間ではない。今回のpprofは親プロセス中心のため、workerのCPU内訳は未確定。

`PUT /api/me/profile-image`のみ、同じjpeg-jsの完全デコードをworker threadへ移す。投稿画像・RealMojiの処理には変更しない。

- アプリプロセスごとに実行枠1つ。本文の`arrayBuffer()`呼び出し前に確保し、待機要求の大きい本文をアプリ側で読み込んでキューに積まない。cluster workerが2つなら検証threadも最大2つ。
- JPEG SOI不一致は従来のdecoderと同じく不正画像として拒否する。SOIがある入力は完全デコードを行う。
- 寸法ヘッダーだけでサイズ超過を早期拒否しない。壊れたサイズ超過JPEGを`invalid_image`として記録する従来の分類を維持するため。完全デコード後、512x512を超える場合は従来どおり400・abuseなし。
- 本文のArrayBufferをworkerへ移し、結果と一緒に同じ本文を戻す。スレッド間で本文をコピーせず、元のbytesをそのままDBへ保存する。
- 検証終了後に既存のDBトランザクションを開始し、行ロック・画像INSERT・プロフィール更新・前画像削除・commitを行う。待機・デコード中はDB接続を確保しない。
- workerは必要時に起動して再利用し、アイドル時はunrefする。HTTP profilerなどのpreloadは検証threadで再実行しない。異常終了はその要求を失敗させ、次の要求で再生成する。
- 待機要求のAbortSignalを受けたらキューから外す。実行中のデコードは終了まで実行枠を保持し、次の要求と重ねない。

新しい画像キャッシュやDB状態は持たず、初期化・永続化・画像配信方式を変更しない。総CPUを削減するものではなく、イベントループの停止を避ける変更。デコード自体のCPU競合、JPEG要求のキュー待ち、初回thread起動コストは残る。

## ローカル検証

- Node.js 26.10.0の型検査成功。最新mainのフィード・Memories変更取り込み後の通常テスト102成功、専用DB等のopt-in試験13スキップ。public候補SQL中のブロック条件を一覧取得と誤認する既存テストモックも修正した。
- 完全decoderとの結果・bytes比較、512/513境界、壊れた大きいJPEGのabuse分類、400/404/415/204応答、保存bytesとDB操作順序を確認。
- CPU検証中の別APIの応答、本文読み込みの直列化、待機/実行中のキャンセル、本文読取失敗、threadのerror/exit後の再生成、close時の待機解放、アイドルthreadがプロセス終了を妨げないことを確認。

`node test/profile-image-worker.bench.ts`で2048x2048の合成JPEGを6試行・順序交互で比較。threadは事前起動し、デコード中のsetImmediateの実行までの待ちを計測した。別テストと同時に実行しない。

| 中央値 | 同期版 | worker版 |
|---|---:|---:|
| デコード完了まで | 282.362ms | 298.400ms |
| イベントループ上のprobe実行まで | 282.443ms | 0.081ms |

合成試験の応答性であり、本番HTTPの遅延や得点改善率ではない。本番反映・追加ベンチは未実施。採否は同条件のベンチで投稿/friends feedの成功・正常APIの遅延・スコア・CPUを比較する。プロフィール画像自体の待ち時間が伸びていないかも確認する。

切り戻しはこの変更のrevertとアプリの再反映。DB migration、nginx変更、データ復元は不要。
