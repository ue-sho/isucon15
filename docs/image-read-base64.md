# 画像取得のDB転送量削減

2026-10-31。キャッシュ未命中の画像取得では、PostgreSQLのbyteaをテキスト形式で受け取るため、画像の約2倍のhex文字列がDBからアプリへ流れていた。`GET /api/images/:imageId` の画像本体を `encode(i.data, 'base64')` で取得し、`Buffer.from(value, 'base64')` で復元する。

キャッシュ命中時は `NULL::text` のみを取得し、画像のエンコード・転送・復元を行わない。署名・期限・所有者の状態・削除・世代・画像行の版の判定を通過してから、復元したバイト列を既存のファイルキャッシュまたは直接応答へ渡す。DBスキーマ変更と追加依存は不要。

## 根拠と測定範囲

調査用のローカルPostgreSQL 16.13、Node v26.12.1、pg 8.23.1で合成データを保存し、同一接続のソケット `bytesRead` 差分を比較した。各条件7回のうち初回を除く6回で測定し、全バイトとSHA256の一致を確認した。

| 元データ | hexのDB応答 | base64のDB応答 | 削減率 |
| --- | ---: | ---: | ---: |
| 200KiB | 409,711 B | 276,769 B | 32.45% |
| 1MiB | 2,097,263 B | 1,416,609 B | 32.45% |

PostgreSQLのbase64出力には改行が含まれる。復元は改行を含む形式に対応する。この数値は転送形式の局所検証であり、WAN遅延・帯域制限や公式ベンチのスコア改善幅を表さない。

既存ベンチ #22237（配布版 `b21e483`）のpprotein group `2026-10-31_06-22-33.64758` では、SQLログ `dmit2w3qiqc1-slowlog.log` の約70秒間に、画像本体を選択するSQLのexecuteが264回、メタデータだけを選択するexecuteが753回あった。parse・bindへの重複出現を除いて数えた。この後に画像再取得・Memories分離の改善が入っているため、現在版のミス率やベンチ全期間の件数とは区別する。

## 検証

- `npm run check`
- `node --test test/image-signature-cache.test.ts test/image-files.test.ts`: 14件成功。
- `IMAGE_SQL_TEST_PORT=<専用ローカルPGポート> node --test test/image_api.test.ts`: 32件成功。

実PostgreSQLのAPIテストは空の専用DBを要求する。JPEG、PNG、0x00・非UTF-8を含む200KiBの合成データ、空データについて、直接応答・ファイル保存・キャッシュ命中・容量不足時の直接応答を検証。既存テストで不正署名・期限切れ・削除・退会・差し替え・鍵変更・初期化・partition pruningも確認する。

本変更でNGINX設定は変更していない。実NGINXを経由する任意テストと共有環境のベンチは未実施。今後の比較では同じ統合版を基準に、海外の画像GET遅延、DB→アプリの転送量、画像取得の採点件数、総スコアを確認する。キャッシュ命中時の性能向上は見込まない。

## 反映と復元

追加DDLは不要。専用ブランチ `perf/image-read-base64` を既存の `task deploy` で反映する。デプロイ後のホストSHAとサービスを確認し、ポータルからベンチを実行する。ベンチはユーザーが実施する。

復元はこの変更をrevertした統合版を反映する。画像ファイルの内容・キー・ディレクトリ形式は従来と同じなので、キャッシュ消去やDB復元は不要。
