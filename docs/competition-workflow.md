# 本番の8時間を改善に使うための運用

目的は、当日に操作方法を作りながら進めず、仕様の理解・計測・改善に集中することです。ISUCON14で使ったTaskfileとスクリプトを引き継ぎ、問題固有の部分を差し替えられる形で事前に通し確認します。以下はIssue #1の実装・練習で満たす要件です。現リポジトリへの操作の接続はまだ行っていません。

## 事前に固める部分と当日設定する部分

| 項目 | 当日までに動かしておくこと | 問題公開後に設定・確認すること |
| --- | --- | --- |
| 環境と権限 | 3人の接続・作業方法、操作の副作用、自律実行の範囲、実行担当と代行 | 許可された接続先、構成・役割、変更可能範囲 |
| ビルド・反映 | 同じソース・設定から成果物を作り、指定版を配置・照合・復元する入口 | 使用言語、ビルド・検証コマンド、配置先、サービス名 |
| ベンチ受付 | 開始・完了待ち・失敗時の結果保存を共通化。CLI、公式受付、手動で受け取る受付IDを差し替えられる形 | 実際の受付方式・引数・認証・初期化条件。別大会の非公開APIを前提にしない |
| 計測・集計 | 1試行の結果・ログ区間・資源観測を同じ識別子で保存。負荷と重い解析を分ける | ログ形式・配置、APIの集約、SQL・資源の観測対象 |
| 排他・通知 | 反映から採取までの共通ロック、短いDiscordサマリー、通知失敗でも原本を残す処理 | 実行対象、共有先、通知してよい内容 |
| CI/CD | CIの検証・成果物作成と、共有環境の反映・計測を分け、共通の操作入口へつなぐ | アプリの検証処理、配布対象、公式の実行条件 |

未知の値があっても、共通の処理と失敗時の扱いは事前に実装・練習できます。未設定の接続先を推測して実行する動作にはしません。CIで一度だけ得点が下がったことを理由に自動判定する閾値は置かず、正しさ・条件・ばらつきと合わせて判断します。

## 3人とAIの分担

初動と終了前は[Issue #2](https://github.com/ue-sho/isucon15/issues/2)を使います。Aが計測・反映・統合、Bがアプリ・仕様、CがDB・データという既存の案を基に、名前と代行者を決めます。負荷の偏りやボトルネックに応じて組み替えます。

各人の調査・ローカル変更は進めつつ、共有環境への操作は実行担当が順番を管理します。人とAIの両方が同じ入口を使います。AIが編集する場所、ビルドする場所、反映する場所を一致させ、別コピーの実装やサーバーだけの変更が増えたら管理対象を整理します。

## 1回の反映・計測で守る順序

```text
環境のロック取得 → 指定版・設定の反映 → 起動と稼働版の照合
→ 計測条件・ログ区間を記録 → ベンチ受付・完了待ち
→ 成功・失敗とも結果を保存 → 採用または必要な復元・動作確認
→ 現在の採用状態を更新 → ロック解除
```

共有環境での初期化・DB変更・ログ退避もこの操作と調整します。Actionsの同時実行制御だけでは手元のSSH操作を調整できないため、共通の環境ロックを使う設計です。集計・ビルド・DDLを別のベンチへ重ねません。障害時にも結果を回収し、サービスや依存先が停止していたら、その事実から切り分けます。

ISUCON14の `task bench` には既にログ退避があります。「ログ全体」という通知の文言だけで、複数試行が混在したとは判断しません。実際の呼び出し・開始終了・退避先を照合し、手動の集計も試行へ対応させます。

## 結果と引き継ぎ

原本は試行ごとに保存し、[メモの雛形](templates/experiment.md)に必要な根拠を残します。

- 試行ID・受付ID・開始終了時刻、対象、実行者。
- コミットと実際の成果物・設定・テンプレート、DB索引・初期化・生成データの条件。
- 終了コード、公式の成功判定、score、failやエラー内訳、messages。存在しない項目は未取得。
- ログ区間・観測のON/OFF・診断プロセス・並行作業、集計と欠損の有無。
- 採否、現在の反映状態、未確認事項、次の一手。

SQLの累積時間とHTTPの経過時間を引き算せず、用途別SQL・実行計画・CPU等で確かめます。長時間接続のAPIは待機を含むため、平均時間だけで重い処理と決めません。ログ無効・欠損は0ではなく未観測です。改善後は負荷の移動先とエラーも見直します。

PRとDiscordには「課題と根拠／変更理由／確認結果と比較条件／採否と現行状態／次の一手」を短く共有し、詳細メモへリンクします。全文の重複転記や、別セッションへ説明し直す作業を増やさないようにします。原本保存を先に完了させ、通知の成否とベンチの成否を分けます。

## 事前の通し確認と本番

練習環境で、基準計測、変更1件、反映、比較、復元を一巡します。起動・ベンチ・集計・通知の失敗でも結果が残るか確認し、別の担当が会話履歴なしで再現します。最小の操作が安定してから反復部分をSkill化し、AGENTS.mdと手順を重複させません。

当日開始時は、[公式レギュレーション](https://isucon.net/archives/59966826.html)と優先される当日マニュアルを読み、構成を接続して無変更の基準を取得します。計測設定の追加前後も区別します。終了前はIssue #2に沿って、残り時間と復元所要時間を見て変更を絞り、採用構成で初期化・再起動・永続性・最終ベンチと必要な提出を確認します。

根拠と参考事例は[練習と公開実践からの知見](lessons-and-sources.md)にまとめています。
