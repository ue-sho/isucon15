# publicフィードの取得件数削減

Issue #19。基点 `174cc85`、ブランチ `perf/public-feed-limit`。

publicフィードは、投稿済み判定後に友達・友達の友達・ブロック一覧を取得し、公開中の投稿候補を全件Node.jsへ転送していた。
publicでは友達関係を使わないため、その読み取りを省略する。候補SQLでpublic・双方向ブロックを判定し、既存の作者active・投稿削除・公開中window・本人除外・cursor条件と合わせてから、posted_at/idの降順でLIMIT 51を適用する。
返す50件だけを署名する既存処理は維持する。

友達がいる投稿済みユーザーのハンドラー内SQLは通常6回から3回（認証済みUserを再利用できる場合は5回から2回）、転送・オブジェクト化する候補は最大51件になる。
関係や投稿のキャッシュは追加せず、次の要求でも現在のDBで判定する。schema・保存方式・initialize・永続化は変更しない。
friends、following、friends-of-friendsは既存経路を維持する。

検証はNode26.10.0と専用PostgreSQL16コンテナで行う。
`test/feed-unposted.test.ts` で既存経路、未投稿、地域/local_date、双方向ブロック、退会、投稿削除、同時刻のID順、複数ページ、50/51件の境界、次の要求へのブロック反映を確認する。
120投稿のfixtureでは、独立した件数無制限のSQL結果と全ページのIDが一致し、各要求のSQLは3回だった。

本番のCPU・RSS・転送量・API時間・競技スコアの改善幅は未計測。共有サーバーへの反映・再起動・初期化・ベンチは未実施。
反映時は対象と実施順を調整して同条件のベンチで比較する。切り戻しは本変更のコード差分を戻して通常手順で再反映する。DB操作は不要。

JPEG（#16）は残件。寸法だけで早期拒否すると、寸法超過かつ破損した画像のinvalid_image記録条件が変わり得るため、今回の変更には含めない。
