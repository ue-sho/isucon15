# 登録・ログインのDB往復削減

registerはusers全体のSHARE ROW EXCLUSIVEロックを、ユーザー名のhashtextextended値をキーとするトランザクションadvisory lockに変更する。ロック取得とは別SQLのINSERT SELECT WHERE NOT EXISTS RETURNINGで、待機後のスナップショットを使って重複を確認する。同名登録は1件だけ成功し、残りは409 username_takenとなる。退会済みユーザー名も予約される。ハッシュ衝突は待機が増えるだけで、名前の比較は元の文字列で行う。正常登録はBEGIN/COMMIT込み5往復から4往復になる。

loginはユーザー行のFOR NO KEY UPDATEを維持し、旧セッションの失効UPDATEと新セッションのINSERTをデータ変更CTEにまとめる。BEGIN/COMMITを含む5往復から4往復になる。INSERTは失効CTEの集計結果を参照するため、旧セッションが0件でも1件作成する。同時ログインを直列化するユーザーロックと、退会との排他は維持する。

## 既存DBへの適用

UNIQUE索引を必要としない。以前のON CONFLICT版は実行先に索引がないと500となるため、この実装へ修正した。001-schema.sqlにもUNIQUE索引を追加しない。既に追加済みの索引はそのままでも動作する。過去のusers-username-uniqueマイグレーションは本修正には不要。

全アプリの登録経路が同じロック方式を使う状態にする。旧ON CONFLICT版との混在中は旧版の500が残る。従来のテーブルロック版へのロールバックはアプリの版を戻すことで行い、DB変更は不要。永続化方式・初期化方式・追加キャッシュの変更はない。

## 検証

通知対象との排他を維持するため、現在は登録時に[通知対象の共有advisory lock](notification-membership-lock.md)も取得する。正常登録はBEGIN/COMMIT込み5往復。名前単位の一意性確認方式は変わらない。

UNIQUE索引のない新規ローカルPostgreSQLで、同名8並列登録が201×1・409×7になることと登録SQLが2件になることを検証する。競技ベンチによるスコア比較は未実施。
