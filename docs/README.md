# 本番まで使う作業の入口

このリポジトリは事前整備と本番の両方で使います。本番の8時間を計測・改善へ使うため、CI/CD、ベンチ・集計・通知、AIの操作手順を事前に組み、3人で通し確認しておきます。問題公開後は、仕様・接続先・言語・構成・公式ベンチの受付方法を確認して接続します。

準備項目は[Issue #1](https://github.com/ue-sho/isucon15/issues/1)、当日の初動・分担は[Issue #2](https://github.com/ue-sho/isucon15/issues/2)を基準にします。docsには操作方法と、各担当が調べたこと・試したこと・結果を残します。NO SHORTCUTとして、本人以外の2人やAIも変更理由と現在の状態を追えるようにします。

## 開始・再開時にそろえる情報

問題公開後、担当が決めた値をここから参照できるようにします。秘密情報そのものは記入しません。

| 情報 | 現在 |
| --- | --- |
| 当日マニュアル・公式回答 | 問題公開後に確認 |
| 編集対象・構成・接続先 | 未設定 |
| ビルド・反映・起動確認・ベンチ・採取・復元の入口 | ISUCON14の既存処理を基に整備する。現リポジトリへの接続・通し確認は未実施 |
| 現在の採用版・設定・DB変更／復元先 | 未設定。計測した版と現在動く版を区別して更新する |
| 進行中の操作・試行／実行担当・バックアップ | 未設定。Issue #2を基に割り当てる |

共通の操作経路と結果保存を事前に動かしておき、当日は問題固有の値と処理を差し替えます。現在のPRは文書を扱い、操作の実装はIssue #1に沿って小さく進めます。

## メモの使い方

1. 一覧から同じ対象の記録と担当を確認します。
2. 新しい調査は雛形を `docs/experiments/` へコピーし、日付と対象が分かる名前にします。例：`YYYYMMDD-topic.md`。
3. 一覧にリンク・担当・状態を追加し、調査や計測の後に結果と次の一手を更新します。

途中でも、分かったことと未確認のことを残せば引き継げます。試したが採用しなかった案も、理由を記録します。メモの作成だけならベンチは不要です。実際の改善では、その変更に必要な確認を行います。PRへは要点を抜粋し、詳細メモへリンクします。
