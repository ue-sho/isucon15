## 最初の変更: 直列DB往復削減

一覧の投稿・作者・コメント・RealMojiは既にJOINまたは一括取得されている。
今回読んだ処理には件数比例のN+1はなく、直列の再取得を削減した。
以下のSQL回数はコードと単体テストで確認したもので、認証・IPBanを除く。

| 処理 | 変更前 | 変更後 |
|---|---|---|
| 現在投稿 | ID→投稿→作者の3 SQL | 投稿・作者をJOINした1 SQL |
| 通知の1ポーリング | activeユーザー→通知の2 SQL | LEFT JOIN LATERALによる1 SQL |

現在投稿は現在地域の公開中枠と投稿枠のlocal_dateを照合する。地域移動前の終了済み枠の投稿も同日なら対象に含める。
通知は通知なしのNULL行と、退会・地域変更による行なしを区別する。接続時刻より後、未終了枠、created_at/idの順序、1件送信で終了、500ms周期は維持する。
通知の接続時間には待機が含まれ、提示されたHTTP集計の時間全体が処理時間とは限らない。
#20記載の通知COMMITと接続開始時刻の競合は既存条件を維持し、今回の変更では解決していない。

## SSEのworker単位一括ポーリング（追加変更）

マニュアルの「通知エンドポイント」「競技環境の変更」「データベースのデータの初期化」を確認。
SSEの通知フィールドと外部仕様を維持し、500ms周期の照会をworker内で共有する。
ハンドラーごとに待機接続だけを保持し、通知データ・ユーザー有効性はキャッシュしない。
複数worker・地域間でも共有DBを都度照会するので、他workerからの書込も次のpollで参照する。

- 接続時のDB時刻取得は接続ごとに1 SQLのまま。待機中のSQLを最大256接続ずつの1 SQLへまとめた。
- 各接続のuser ID・接続時刻・地域を配列で渡す固定SQL。通知のcreated_at > connectedAt、未終了枠、created_at/id順を維持。
- 同一ユーザーの複数接続も個別の接続時刻で判定。ユーザー無効時は終了、通知なしは待機、1件送信後に終了。
- タイマーと実行中照会を各1つに制限。256件を超えた場合も順次実行し、照会を重ねない。
- AbortSignalとReadableStream.cancelの両方で接続を除去。SQL実行中に切断された接続へは送信しない。全切断時はタイマー停止。
- 通知内容を保存しないため追加のキャッシュ初期化・永続データ復元は不要。DB初期化・再起動の方式は変更しない。
- #20に記載した、作成時刻とCOMMITの間に接続する既存競合は今回も未解決。時刻条件を勝手に変更しない。

追加検証: notification-batch.test.tsで100接続=1 SQL、257接続=2 SQLを確認。
同一ユーザー複数接続、遅いSQL中の追加/切断、poll非重複、配信後/全切断後の停止を確認。
実DBテストでも同一ユーザーの2接続に異なる接続時刻を与え、通知時刻と等しい場合は除外、1マイクロ秒前なら配信を確認。
実DBテストは実行ごとに新規の `isureal_roundtrips_<timestamp>` DBを作成するよう更新した。
本番反映・実負荷・PostgreSQL16の実行計画・スコアは未確認。

最終差分の検証は追加・更新テスト計10件成功、型チェック・diff check成功。
