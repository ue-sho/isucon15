## 変更と正しさ

変更する製品コードは webapp/nodejs/src/image_signature.ts のみ。
公開関数の引数・戻り値・同期性、署名の1000段HMAC-SHA256、URLの24時間有効期間・秒精度・エスケープは維持する。

cache key は JSON.stringify([鍵の全バイトをhex化した文字列, imageID, String(exp)])。
JSONによりフィールド境界とUnicodeの正確な文字列表現を保存する。鍵のBufferオブジェクトの同一性には依存しない。
数値expと、その数値を既存実装と同じ文字列にしたexpは同じ署名入力なので共用する。
先頭ゼロ、プラス、指数、空白、小数表記等を正規化して同一キーへまとめない。
安全な整数の標準表記で現在時刻より後のexpだけを保存し、それ以外も従来の式で計算して返す。
これは保存対象の選択であり、URLの受理・拒否判定を変更するものではない。

- workerごとのLRU、最大2,048件。
- 保存データ予算2MiB。1件の計上量は「2 × (JSONキー長 + hex署名長) + 256 bytes」。UTF-16相当の文字列量と固定費を見積もる。Map/V8管理領域、GC中の一時領域、返却Buffer、プロセス全体のRSSの厳密な上限ではない。
- 鍵hex相当の長さ + imageID長 + exp文字列長が4,096文字を超える入力は保存しない。JSONエスケープ後の文字列長で予算を計算し、予算を超える単体エントリも保存しない。
- 保存時から単調時計で60秒未満、かつ元のexpが未来である間だけ再利用。命中でTTLを延長しない。URLのexpは一切丸めたり延長したりしない。
- 期限切れは再利用しない。TTL切れの同一キー再参照や容量超過で削除する。URL期限を過ぎて保存対象外になったエントリや未参照エントリが物理的に残る場合も件数・予算内。掃除用タイマーや全件走査は追加しない。
- 内部署名は不変のhex文字列。missの戻り値やhitで作ったBuffer、さらにそのbacking ArrayBufferを書き換えても保存済み署名を壊さない。鍵の内容変更は別キーになる。
- 署名検証結果、active状態、画像有効性、閲覧権限、DBの行、画像本体は保存しない。

image_api.ts は引き続き毎回、形式・期限、所有者のactive状態と現在の鍵、timingSafeEqual、画像の有効性SQL、返却直前の期限を確認する。
削除・退会・RealMoji差替えをキャッシュが隠す経路は追加していない。実DBの振る舞いは別途検証する。

## 初期化・鍵変更・worker

**計算結果としての再利用は初期化の前後で正しいが、キャッシュ実体の初期化は統合前の残件。**

署名は鍵の内容・imageID・expの3入力だけで決まり、DBの世代や画像の状態には依存しない。
初期化で同じ3入力が復元されれば同じバイト列、新しい鍵や画像IDなら別エントリになる。
画像IDが再利用されても権限・存在・有効性は現在のDBで毎回判断する。
鍵を変更した後に元の鍵へ戻した場合にも、元の3入力への署名は変化しない。以上を合成入力と偽DBで検証した。

main.ts は cluster.fork によりプロセスを分けるので、キャッシュは共有されない。
別workerでmissしても同じ署名を計算でき、worker間で同期する必要はない。再起動後は空キャッシュから再計算でき、永続化対象ではない。
2 workerなら保存データ予算は1台あたり4MiB、3台×2 workerなら計12MiBに相当する。ただし実worker数とRSSは別途確認し、V8等の追加分を考慮する。

[現行公式マニュアル](https://gist.github.com/whywaita/17f3ab1a8c1b7585c571f4f8afe5f531)の「データベースのデータの初期化」「負荷走行の実行」は追加キャッシュの初期化も求める。
2026-10-31にGitHub APIで関連節を再確認した。計算結果が同値であることだけをもって、この文言への適合が確定したとは扱わない。
今回initializeと共通設定は編集禁止なので、全リージョン・全workerへ消去を伝える処理は追加していない。
**共有環境への適用前に、統合担当がこの要求を解決すること。** 実体消去を行う場合は全workerへの通知・完了確認を伴う初期化を別変更として用意する。
単一workerのMapだけを消す処理では不十分であり、TTLによる失効やデプロイ時の再起動だけをinitialize対応済みとはしない。
initialize.ts の既存 agent/harness/model 申告が human/manual/brain である点も、AI利用の申告更新を統合担当へ引き継ぐ。

### ローカルマイクロベンチ

全入力は合成データ。旧実装は専用referenceファイルに保存した基点の計算と同じもの。
測定対象の image_signature.ts のGit blobは 199bed7cb304c9b283bf777885350e2bed488198。
各ケース3,000回、実装/ケースごとに別プロセス、3試行、実装の実行順を交互にする。
100回の予熱は測定対象と別入力。測定前後にGC、CPU時間・経過時間・heap/RSS・ArrayBufferを計測する。
ピークは250回ごと＋開始/終了のサンプルであり、厳密な最大値ではない。
8組の反復ケースは初回8 missを含み、2,992 hit（99.73%）。全異種ケースは0 hit。
実装間の出力チェックサム一致も確認する。精密な同値性は別のテストで検証する。

反復入力の計算省略は明確。全異種の改善は確認できず、保存データと一時文字列のコストが増える。
RSS差分の負値はGC等による測定前後の変動であり、実装の負のメモリ使用を意味しない。
生の合成計測結果はローカルの /tmp/isucon15-image-signature-cache-bench-final.jsonl（Git対象外）。入力・鍵・署名は出力しない。

RSSはアロケーターやGC、共有ライブラリの影響を含み、保存データ予算2MiBと一致しない。
長い異種入力ではキャッシュ導入によるメモリ増加があるため、本番で全workerのRSS・GCを確認する。
